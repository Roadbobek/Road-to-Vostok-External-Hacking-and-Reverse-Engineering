GameData.tres is a Resource. Resources in godot are handled by Reference Counting. this means the resource lives in its own dedicated block of memory, completely independent of the game world. The player node, the HUD, and the save system all just point to this single, shared block of data.
GameData.gd defines what the variables are (compiled into the layout of the memory block).
GameData.tres is the actual location in RAM where those variables live while the game is running. because every script preloads this exact .tres file, editing that one memory block instantly updates the player, the HUD, the save system, and everything else simultaneously.
the original memory address that stores the health variable (29CDDA03FA8) is purely temporary, it lives on the computers heap in memory. whenever you restart the game, return to main menu, or do anything that will remove GameData.tres from memory godot will recreate GameData.tres at a completely different address, like 3B4FD21A0F8 for eg.
thats why we need the pointer to point to the memory region instead of just having a static address. going back to (["RTV.exe"+0638B920] -> 29CE9F6E8C0) and our 5 offsets ([offset 0: 168], [offset 1: 0], [offset 2: 78], [offset 3: 988], [offset 4: 6F8]), lets break this down.
"RTV.exe" : is the Module Base Address. this is the starting line where windows loads the game into RAM. it changes every single time the game restarts because of ASLR.
0638B920 : is the Module Offset (Relative Virtual Address / RVA). it is a hardcoded byte distance compiled into the binary being the executable / application.
because windows maps the executable file directly into RAM byte for byte, this offset tells you and cheat engine exactly how many bytes to calculate forward from the Module Base Address to land on the global static pointer.
"RTV.exe" + 0638B920 : is the Static Pointer Address. It’s the math equation that targets the permanent, unmoving memory address where our pointer chain begins.
-> 29CE9F6E8C0 : is the First Resolved Address. this is the dynamic memory address stored inside your global static pointer slot, its the resulting number / address stored inside the memory address thats calculated by adding the Module Base Address ("RTV.exe") and the Module Base Offset (0638B920) together.
cheat engine then uses it as the base address to calculate the final Target Address using the Offsets, the Target Address is our health variable in this example. We dont need to store this as it is dynamic and calculated by our past equation. it is an important part in the process thats why i mention it, everything else we need to save tho.
The 5 offsets (168, 0, 78, 988, 6F8) : are the Multi-Level Pointer Offset Chain. in Godot, scripts and resource files are nested inside each other as data structures in memory. These offsets are the exact byte-distances used to navigate through those layers.
the chain starts at the engine's core memory block, navigates through the active script instances, jumps directly into the loaded structure of your GameData.tres resource file, and the final offset (6F8) lands directly on the health float variable stored inside it.
instead of just adding all the offsets together into one big number, the calculation alternates between adding an offset and dereferencing (reading the memory address stored inside).
heat engine calculates it in a loop like this:
calculate and read: It calculates "RTV.exe" + 0638B920 and looks inside to read the address stored there (29CE9F6E8C0).
add Offset 0: It adds 168 to 29CE9F6E8C0. it looks inside this new address to read the next destination address.
add Offset 1: It takes that new address, adds 0, and looks inside it to read the next destination address.
repeat: It does the same thing for offsets 78 and 988 always adding the number, then reading the address found inside.
final Step: It takes the final address, adds the last offset (6F8), but does not look inside. adding this final offset lands it exactly on the target address (29CDDA03FA8) where your health value sits.
By reading the value inside at every step, the calculation is able to follow the links from one separate memory block to another across the heap, and this is how we bypass ASLR.

ASLR is a low level security defense mechanism implemented by the operating system kernel and enforced by the CPUs Memory Management Unit (MMU).

What is RDX?
RDX is a hardware register—a tiny, 64-bit storage slot physically built inside your computer's CPU processor chip. It is not an address in RAM; it is a temporary scratchpad the CPU uses to hold data while executing instructions.
When the CPU executes mov [rdx+08], r8d:
RDX holds a 64-bit Heap Memory Address (e.g., 0x000001FD8B2A1040). This address points to the start of the Viewport object in your system's RAM.
r8d holds the Horizontal Resolution integer (e.g., 2560).
[rdx+08] means: "Take the address in RDX, go 8 bytes forward in RAM, and write the value 2560 there."
Why does it write to [rdx+08] instead of [rdx]?In C++, when an object (like a Viewport or Window class) is allocated in memory, its variables are laid out end-to-end in RAM.RDX holds the base address (offset +0x00) where the object starts. Moving 8 bytes ahead (+0x08) happens for two main reasons in 64-bit object-oriented code:1. The 64-bit VTable Pointer (Offset +0x00 to +0x07)In 64-bit C++, whenever a class uses virtual functions, the compiler automatically inserts an 8-byte VTable Pointer (vftable) as the very first item at the top of the object.Bytes 0 through 7 store the pointer to the object's function blueprint.Therefore, the object's actual data fields (variables) can't start until byte 8 (+0x08)!2. some quick notes on assembly,
in x86/x64 assembly, instructions read from right to left.
no brackets 'rdx', refers to the register itself, you are accessing the 32 or 64 bit value currently stored directly inside the cpus register, for eg 'mov rax, rdx' copies the value inside the rdx register into the rax register all in / on the cpu.
with brackets '[rdx]', refers to memory dereferencing, the cpu treats the value inside the register as a memory address, it is a pointer, it goes to that specific location in ram/memory and reads the data stored there or writes to it, for eg 'mov rax, [rdx]' copies the value found at the memory address stored in rdx to rax.
with offset '[rdx + 0x8]', refers to memory dereferencing with displacement, the cpu takes the address in rdx, adds 8 (bytes) to it, and accesses the memory at that calculated location. This is commonly used to access fields within a data structure or array, for eg 'mov rax, [rdx + 0x8]' accesses the memory 8 bytes after the address stored in rdx and copies it to rax.
32-bit registers start with E or end with D, for eg 'eax, edx, r8d, r9d, r8d', in modern games, almost every 64 bit value is a memory address / pointer (like 0x00000222D06A0E60).
64-bit registers start with R, but apply above rules first, for eg 'rax, rdx, rsi, r8, r9', in modern games these hold regular game variables (like horz res 2560, health 100, or ammo 30).
remember that cpu registers hold binary data so 1s and 0s, though they are often shown as hex for human readability, hexadecimal is simply a shorthand notation, one hex digit corresponds exactly to four binary bits.
ram / random  access memory is the same as ofc it stores binary, also remember in reference to assembly every byte in ram has a unique binary address that allows the cpu to locate and retrieve specific data blocks to load into its registers for processing.
